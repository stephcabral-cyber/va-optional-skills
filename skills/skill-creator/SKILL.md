# Skill Creator

**Version: 1.1 - 2026-10-19** (get the steps from the owner before writing any: if they were not given, ask which of the three ways the owner wants, SOP, describe it, or let you watch, and never fill steps in from guesses; this applies when the request arrives through the prompt writer too)

**What's new for you (1.1):** When you ask Vera to build a skill, she now makes sure she has your real steps before she writes it. If you haven't given them yet, she'll ask how you want to: upload an SOP, describe it by typing or talking, or let her watch you do the work. It saves time to say it up front, like "build a skill for my move-in checklist, I'll upload my SOP."

A skill is a written playbook. It turns something the owner has to explain every time into something
that is simply known. **The goal is to turn as much of the repeatable work as possible into skills**,
because everything still living in somebody's head has to be re-explained, and eventually gets
re-explained slightly wrong.

## Before you write a single step: get the steps from the owner

**A new skill is built from the owner's real process, never from your idea of how the job is usually
done.** Before writing any steps, check whether you actually have them. If you do not, stop and ask
how the owner wants to give them to you. There are three ways, and the owner picks:

1. **Upload an SOP.** A written procedure, a checklist, an old training doc. Read it, then ask only
   about the blanks it leaves.
2. **Describe it.** Typed or by voice, in their own words. Let them be loose and ask follow-ups
   afterwards rather than interrupting.
3. **Let you watch.** They do the work while you observe and they narrate, which is often best inside
   software. Build the steps from what you see and what they say.

- **Ask in one short question, with the three options,** using the tappable question tool when there
  is one. If the owner already said which way in their request ("I'll upload my SOP"), skip the
  question and go straight to it.
- **This applies when the request arrives through the prompt writer too.** The prompt writer improves
  how the request is worded; it does not collect the process. A beautifully written prompt that says
  "build a skill for X" still has no steps in it. Check, and ask.
- **Fuzzy is allowed, guessing is not.** The owner can leave a decision open ("I'll decide that
  later"). Write it into the skill as an open question, clearly marked, and keep going. Never fill the
  gap with a plausible invention.
- **If the owner says "stop asking, make your best guesses",** do that, and finish with a short list of
  every step you guessed so they can correct them.
- **Why this is a hard rule:** a skill written from guesses reads exactly as confident as one written
  from the owner's real process, so nobody notices until it does the job the wrong way. The steps are
  the one part of a skill only the owner can supply.

**Then test it before it touches anything real:** run it once on sample data, show the owner the
result, and fix what they correct.

## What actually belongs in a skill

**A skill holds knowledge that would otherwise be rediscovered.** That is the whole test.

- **How this tool really behaves**, especially where it behaves differently from how it looks.
- **The traps.** Anything that cost time once and would cost it again.
- **The decisions already made**, so they stop being reopened.
- **The order things have to happen in**, when the order matters.

What does not belong:

- **What happened today.** That is a note, not a skill.
- **Anything specific to one record, one person, one month.** Skills outlive them.
- **Anything already obvious from looking at the tool.** A skill that restates the interface is
  padding, and padding is what stops skills being read.

**The strongest test at the end of any piece of work: did we learn something about a tool that is not
yet written down? If yes, write it before finishing.** That single habit is the difference between a
system that gets better every week and one that relearns the same lesson every month.

## The placeholder pattern

Most owners know which tools they will need long before they get to them. Somebody knows they will
eventually automate their rent platform, but that is three weeks away. **Do not wait, and do not
write a fictional skill either.**

**Create a placeholder.** A short, honest file that says:

- **What the tool is and what it is for in this business**, in a sentence or two.
- **What we already know**, even if that is very little. Whether there is a connector. Whether
  sign-in is awkward. What the owner has said they want it to do.
- **What is not known yet**, named explicitly, so the next session knows what to find out rather than
  guessing.
- **A clear line at the top saying this is a placeholder** and has not been proven against the real
  tool.

**Then put it in the parking lot on the hub.** A row in the owner's skills list, marked as parked,
with the same name as the folder. That row is what stops the placeholder being forgotten, and it is
what makes the queue of unwritten skills visible instead of imaginary.

**A placeholder must never read like a finished skill.** Anything in it that has not been tested says
so. The worst outcome here is a confident file full of invented behaviour, because the next session
trusts it and builds on sand.

## Filling a placeholder in

**The moment the owner actually works on that tool or that process, the placeholder is what you open
first, and filling it in is part of the job, not a separate task afterwards.**

This is the point of the whole pattern. The knowledge is never as available as it is right now, while
the thing is in front of you and the surprise is fresh.

1. Open the placeholder before touching the tool.
2. Do the work.
3. **Write down what actually happened**, especially anything that surprised you: what the tool did
   differently from what was expected, what failed, what the working path turned out to be.
4. Take the line about it being a placeholder off, and move the row out of the parking lot.

**A placeholder that stays a placeholder through three sessions of real work on that tool is a
process failure, not a scheduling problem.** It means the writing step is being skipped.

## Writing one well

- **Say the rule and then say why.** A rule with no reason gets overridden by the next person who
  thinks they know better. A reason makes it stick.
- **Lead with what goes wrong.** People read a skill when something is confusing, so the traps belong
  near the top, not in an appendix.
- **Plain sentences beat dense shorthand.** These are read by somebody who may be new to all of it.
- **No specific numbers, thresholds, deadlines or points of law.** Those change, they vary by place,
  and a confidently wrong one is worse than no answer. Say what the thing depends on and who decides
  it.
- **Nothing that identifies one business.** No keys, no account names, no real people, no record
  identifiers. These files get shared.
- **A diagnosis table at the end earns its keep**, because that is what somebody reads at the moment
  they are stuck.

## Improving one

**Improving a skill means finishing it and shipping it**, not producing a proposal about it.
Restructure it if it needs restructuring. Read it end to end more than once. Then ship it.

- **When two files say the same thing, they will disagree within a week.** Say it in one place and
  point at it from the other.
- **Anything appended at the bottom over time eventually needs reorganising**, because the useful
  material ends up furthest from where anyone reads.
- **Version it, and bump the version in the skills list in the same breath**, or nothing can tell
  what changed.

## Telling a good skill from a dead one

- **A good skill gets loaded.** If a skill exists and nobody ever reaches for it, either its
  description does not match how people actually ask, or it should not exist.
- **The description is what makes it trigger.** Write it as the words the owner really uses, not the
  official name of the tool. Somebody says "did they pay", not "query the payment platform".
- **Length is not quality.** The best skills here are short and dense with things that are not
  obvious.

## Diagnosis

| What you see | What it usually is | What to do |
|---|---|---|
| The same explanation is being given again | It never got written down | Write it now, while it is fresh |
| A new skill does the job differently from how the owner does it | It was written from guesses, not the owner's steps | Ask for the steps (SOP, describe, or watch) and rewrite it from those |
| A skill exists but never gets used | Its description does not match how people ask | Rewrite the description in the owner's own words |
| A placeholder is still empty after real work happened | The writing step is being skipped | Fill it during the work, not after |
| Two skills contradict each other | The same rule was written in both | Keep one, point at it from the other |
| A skill confidently describes behaviour that turns out to be wrong | It was written from assumption, not from use | Mark what has actually been tested and what has not |
| Nobody knows which skills exist | There is no list | Keep the skills list current, including the parked ones |
